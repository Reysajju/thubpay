### Stage 4 — Phase 1 #3: Webhook dispatcher retry + Idempotency-Key (NEW reliability feature)

**Goal:** Phase 1 worklog identified that the webhook dispatcher had no retry — single attempt per endpoint. This is a major reliability gap.

**Schema changes** (`prisma/schema.prisma`, model `WebhookDelivery`):
- Added `attempts Int @default(1)` — count of delivery tries so far (1 = first attempt).
- Added `nextRetryAt DateTime?` — null when no more retries scheduled.
- Added `idempotencyKey String?` — value of the Idempotency-Key header sent to the endpoint, so endpoints can dedupe retries.
- Added `@@index([nextRetryAt])` for efficient cron sweep queries.

Ran `bun run db:push` (24ms, in sync) and `bun run db:generate` (Prisma Client v6.19.2 regenerated).

**Dispatcher changes** (`src/lib/webhook-dispatch.ts`, full rewrite ~340 LOC):
- Exported `MAX_WEBHOOK_ATTEMPTS = 7`.
- Exported `BACKOFF_SECONDS = [30, 120, 600, 3_600, 21_600, 86_400]` — exponential backoff: 30s, 2m, 10m, 1h, 6h, 24h.
- Exported `computeNextRetryAt(attemptsSoFar)` — returns `Date | null` (null when `attempts >= MAX`).
- Exported `computeIdempotencyKey(eventId, endpointId, attemptNumber)` — `sha256(\`${eventId}|${endpointId}|${attemptNumber}\`)`. Stable per (event, endpoint, attempt) tuple so endpoints can dedupe retries.
- `dispatchWebhookEvent()` now passes `attemptNumber = 1` to `deliverOne()` on first dispatch.
- `deliverOne()` now sends two new headers:
  - `X-ThubPay-Attempt: ${attemptNumber}` — endpoint can see which attempt this is.
  - `Idempotency-Key: ${idempotencyKey}` — endpoint can dedupe.
- On failure, `deliverOne()` computes `nextRetryAt` via `computeNextRetryAt(attemptNumber)` and persists it in the new `attempts`/`nextRetryAt`/`idempotencyKey` columns.
- NEW exported function `retryDueDeliveries(batchSize = 50): Promise<RetrySweepResult>` — scans for failed deliveries where `nextRetryAt <= now` AND `attempts < MAX_WEBHOOK_ATTEMPTS`, retries each by calling `deliverOne` with `attempt + 1`, and updates the existing delivery row in-place (rather than creating a new row per retry — keeps the audit trail compact). Returns aggregate `{ total, retried, succeeded, failed, exhausted, results[] }`.
- NEW exported function `retryDeliveryById(deliveryId): Promise<{ ok, status, error?, attempts? }>` — manual single-delivery retry, used by the admin UI's "Retry now" button. Bypasses the nextRetryAt schedule.

**New cron endpoint** (`src/app/api/cron/webhook-retry/route.ts`, 70 LOC):
- `GET/POST /api/cron/webhook-retry` — calls `retryDueDeliveries(100)` and returns aggregate stats. Auth: optional Bearer token via `CRON_SECRET` (tolerates unauthenticated in dev). `maxDuration = 60`.

**New admin retry endpoint** (`src/app/api/dashboard/webhooks/deliveries/[id]/retry/route.ts`, 50 LOC):
- `POST /api/dashboard/webhooks/deliveries/[id]/retry` — requires workspace auth, verifies the delivery belongs to the workspace, rejects if `attempts >= MAX_WEBHOOK_ATTEMPTS` (HTTP 409 with `{ status: 'exhausted' }`), short-circuits if `status === 'ok'` (returns `{ ok: true, status: 'already_ok' }`). Otherwise calls `retryDeliveryById` and returns the result.
